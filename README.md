# دعوة زفاف يوسف وشذى 💍

موقع دعوة زفاف إلكترونية بالعربية (RTL) بهوية **Emerald** الزمردية، مع نظام تأكيد حضور (RSVP)
وقاعدة بيانات مشتركة على **Supabase**، ولوحة تحكم إدارية محمية.

| المعلومة | القيمة |
|---|---|
| العريس / العروس | يوسف / شذى |
| التاريخ | الخميس 27 مايو 2027 (ميلادي) |
| الوقت | 16:00 بتوقيت `Asia/Baghdad` (= 13:00 UTC) |
| القاعة | مزرعة الفرح — العابات على نهر دجلة |
| مدة الحفل | **غير محددة** (إعداد قابل للتعديل) |
| رابط خرائط دقيق / رقم واتساب | **غير محددين** (إعدادات اختيارية) |

> ⚠️ **ما يحتاج إلى استكمال من صاحب المشروع** (لم يُخترع أي منه):
> 1. إنشاء مشروع Supabase وإدخال الرابط والمفتاح العام.
> 2. إنشاء حساب المدير الأول (البريد وكلمة المرور تختارهما أنت).
> 3. رابط Google Maps الدقيق للقاعة — حاليًا يُستخدم رابط **بحث** باسم القاعة والعنوان.
> 4. مدة الحفل — حاليًا ملف التقويم يستخدم 4 ساعات **تقديرية** مع تنبيه بذلك.
> 5. (اختياري) رقم واتساب ودومين مخصص.

## المزايا

**صفحة الدعوة** (`/`)
- افتتاحية بآية كريمة، أسماء العروسين بخط «عارف رقعة»، زخارف نباتية ذهبية (SVG خفيف).
- التاريخ والوقت والقاعة والعنوان، وعدّ تنازلي (أيام/ساعات/دقائق/ثوانٍ) يُحسب **بتوقيت بغداد** مهما كانت منطقة جهاز الزائر.
- أزرار: خرائط Google، إضافة إلى التقويم (ملف ICS + Google Calendar)، مشاركة عبر واتساب، نسخ نص الدعوة.
- قسم **«ملاحظة مهمة لضيوفنا الكرام»** بالنص الحرفي المطلوب، قبل نموذج الرد مباشرة، ومُضمَّن في رسالة واتساب والنص المنسوخ.
- نموذج **«هل ستشاركوننا فرحتنا؟»**: الاسم، الحضور/الاعتذار، عدد **البالغين** (يظهر عند الحضور فقط)، رسالة اختيارية.
- حالات تحميل ونجاح وخطأ، منع الضغط المزدوج، حفظ المسودة عند الأخطاء المؤقتة، ولا تُعرض رسالة نجاح إلا بعد تأكيد الحفظ من الخادم.
- متجاوب بالكامل، يدعم لوحة المفاتيح وقارئات الشاشة، ويحترم «تقليل الحركة».

**لوحة الإدارة** (`/admin/`)
- تسجيل دخول عبر Supabase Auth (لا يوجد تسجيل حساب جديد من الواجهة).
- بطاقات: إجمالي الردود، المؤكدون، المعتذرون، إجمالي البالغين المتوقع، المتوسط لكل رد مؤكد، الدعوات التي لم تُرد (تظهر فقط عند وجود دعوات شخصية).
- رسوم بيانية: المؤكدون مقابل المعتذرين، تطور الردود يوميًا، تراكم عدد البالغين المتوقع — مع حالة فارغة واضحة عند عدم وجود بيانات.
- جدول بالبحث والتصفية والترتيب وتقسيم الصفحات، وعرض التفاصيل، والتعديل، والحذف بتأكيد، وإضافة رد يدوي (مثل رد عبر الهاتف).
- إنشاء دعوات شخصية بروابط سرية، إلغاؤها، أو إصدار رابط جديد.
- **تعديل كل محتوى الصفحة من اللوحة**: الأسماء، التاريخ والوقت، القاعة والعنوان ورابط الخرائط، الآية والنصوص، عناوين الأقسام، ملاحظة الأطفال (أو إخفاؤها)، رقم واتساب ورابط الموقع والعبارة الختامية، وإعدادات الردود.
- سجل عمليات إداري إلحاقي (لا يُعدَّل ولا يُحذف).
- تصدير CSV بترميز UTF-8 (يدعم العربية في Excel) مع حماية من حقن الصيغ.

## كيف يعمل النظام (البنية الأمنية)

```
 الزائر (index.html)                       المدير (admin/)
       │  POST {action: context|submit}          │ supabase-js + JWT المدير
       ▼                                          ▼
 Edge Function "rsvp"  ──(service_role)──►  PostgREST ◄── RLS: is_admin() فقط
   • تحقق من المدخلات                         │
   • حقل فخ للروبوتات                         ▼
   • تحديد معدل لكل IP (مجزّأ)          PostgreSQL
   • CORS بالنطاقات المسموحة            • قيود CHECK + محفزات
       │                                 • دوال SECURITY DEFINER
       ▼                                 • سجل تدقيق إلحاقي
  rsvp_submit / rsvp_get_context  (ممنوحة لـ service_role فقط)
```

- الزائر المجهول (`anon`) **لا يملك أي صلاحية** على أي جدول أو دالة؛ حتى لو استخدم المفتاح العام مباشرة مع REST API.
- الردود العامة تمر حصرًا عبر الـ Edge Function، التي تستدعي دوال قاعدة بيانات تعيد التحقق من كل شيء.
- المدير يُعرَّف بوجوده في جدول `admin_users`، وكل سياسة RLS ودالة إدارية تتحقق من `is_admin()` في الخادم.
- مفتاح `service_role` موجود فقط داخل بيئة الـ Edge Function على Supabase (يوفره Supabase تلقائيًا)، ولا يظهر في أي ملف بالمشروع.

## التشغيل المحلي السريع

المتطلبات: **Node.js 18+** فقط لعرض الموقع.

```bash
# 1) فك الضغط والدخول للمجلد
unzip wedding-invitation.zip && cd wedding-invitation

# 2) تشغيل خادم محلي (بدون تثبيت أي حزم)
node scripts/serve.mjs
# افتح http://localhost:5173  ولوحة الإدارة http://localhost:5173/admin/
```

قبل ربط Supabase ستعمل الصفحة بالكامل (التصميم، العد التنازلي، الخرائط، التقويم، واتساب، النسخ)،
بينما يعرض نموذج الرد رسالة صريحة: «نظام تأكيد الحضور لم يُربط بالخادم بعد» ولا يرسل شيئًا.
لا تفتح `index.html` مباشرة كملف (`file://`)، لأن وحدات JavaScript تحتاج خادمًا.

## إعداد Supabase خطوة بخطوة

### 1. إنشاء المشروع
1. أنشئ حسابًا على <https://supabase.com> ثم **New project**.
2. اختر منطقة قريبة من الضيوف (مثل Frankfurt `eu-central-1`) وكلمة مرور قوية لقاعدة البيانات واحفظها.

### 2. تنفيذ ملفات SQL (بالترتيب)

**الطريقة أ — من لوحة Supabase (الأسهل):**
افتح **SQL Editor → New query**، والصق محتوى كل ملف ثم **Run**، بهذا الترتيب تمامًا:

| الترتيب | الملف | ماذا يفعل |
|---|---|---|
| 1 | `001_initial_schema.sql` | الجداول، القيود، الفهارس، محفزات التطبيع و`updated_at` وفرض الحد الأعلى |
| 2 | `002_security_policies.sql` | جدول المدراء، `is_admin()`، تفعيل RLS، سحب الصلاحيات الافتراضية، السياسات |
| 3 | `003_audit_log.sql` | تسجيل العمليات الإدارية وحماية السجل من التعديل والحذف |
| 4 | `004_rsvp_public_api.sql` | دوال RSVP الآمنة وتحديد المعدل (لـ service_role فقط) |
| 5 | `005_admin_api.sql` | الإحصائيات وإنشاء الدعوات وتجديد روابطها (للمدير فقط) |
| 6 | `006_seed_wedding_settings.sql` | إدخال بيانات الزفاف (لا يضيف أي ردود) |
| 7 | `007_editable_content.sql` | جعل كل نصوص الصفحة وعناوينها وخيارات المشاركة قابلة للتعديل من لوحة الإدارة |

> إن كنت نفّذت الملفات 1–6 سابقًا، نفّذ `007_editable_content.sql` فقط؛ يحتفظ ببياناتك ويضيف الحقول الجديدة بقيمها الحالية.

الملفات قابلة لإعادة التشغيل دون أضرار (تم التحقق من ذلك آليًا).
**لا تنفذ** ملفات `supabase/tests/` على Supabase؛ فهي لمحاكاة البيئة محليًا فقط.

**الطريقة ب — Supabase CLI:**
```bash
npm i -g supabase            # أو brew install supabase/tap/supabase
supabase login
supabase link --project-ref YOUR-PROJECT-REF
supabase db push             # ينفذ supabase/migrations بالترتيب
```

### 3. التحقق من سياسات الأمان
في **Table Editor** يجب أن يظهر شعار **RLS enabled** على الجداول الستة:
`wedding_settings`، `invitations`، `rsvp_responses`، `admin_audit_logs`، `admin_users`، `rsvp_rate_limits`.
ويمكنك التحقق من SQL Editor:
```sql
select relname, relrowsecurity from pg_class
where relnamespace = 'public'::regnamespace and relkind = 'r';
-- يجب أن تكون relrowsecurity = true لكل الجداول
```

### 4. نشر الـ Edge Function
```bash
supabase functions deploy rsvp --no-verify-jwt
```
`--no-verify-jwt` ضروري لأن المدعوين ليسوا مستخدمين مسجلين (وهو مضبوط أيضًا في `supabase/config.toml`).

### 5. ضبط أسرار الدالة
```bash
cp .env.example .env     # ثم عدّل القيم
supabase secrets set RSVP_IP_SALT="$(openssl rand -hex 32)"
supabase secrets set ALLOWED_ORIGINS="https://your-domain.example,https://www.your-domain.example"
supabase secrets set RSVP_SUBMIT_LIMIT=10
```
- أثناء التطوير المحلي أضف `http://localhost:5173` إلى `ALLOWED_ORIGINS`.
- إن لم تضبط `ALLOWED_ORIGINS` تقبل الدالة كل النطاقات (`*`) — يُفضّل تقييدها بعد النشر.

### 6. إعدادات المصادقة (مهم)
في **Authentication → Providers/Sign In**:
- **عطّل** «Allow new users to sign up». (حتى لو لم تُعطّل، لا يحصل أي مستخدم جديد على صلاحيات؛ لكن التعطيل يمنع إنشاء حسابات عشوائية.)
- أبقِ تسجيل الدخول بالبريد وكلمة المرور مفعّلًا.

في **Authentication → URL Configuration** ضع `Site URL` = رابط موقعك المنشور.

## إنشاء حساب المدير الأول

لا تحتوي الواجهة أي وسيلة لإنشاء مدير، ولم تُخترع أي بيانات دخول.

1. **Authentication → Users → Add user → Create new user**: أدخل بريدك وكلمة مرور قوية (12 حرفًا فأكثر) وفعّل **Auto Confirm User**.
2. افتح `supabase/admin/create_first_admin.sql`، استبدل `REPLACE_WITH_ADMIN_EMAIL@example.com` ببريدك، ونفّذه في **SQL Editor**.
   (لا تحفظ الملف المعدّل في Git.)
3. سجّل الدخول من `/admin/`. لإضافة مدير ثانٍ (مثلًا العريس والعروس معًا) كرر الخطوتين.

سحب الصلاحية:
```sql
delete from public.admin_users where user_id = (select id from auth.users where email = 'x@example.com');
```

## ربط الواجهة بقاعدة البيانات

من **Project Settings → API** انسخ:
- **Project URL** مثل `https://abcd.supabase.co`
- المفتاح العام **anon** (أو **publishable**) — هذا مفتاح عام مصمَّم ليكون في المتصفح.

ثم إما:
```bash
# املأ PUBLIC_SUPABASE_URL و PUBLIC_SUPABASE_ANON_KEY في .env ثم:
node scripts/configure.mjs      # يرفض تلقائيًا أي مفتاح service_role/secret
```
أو عدّل `js/config.js` يدويًا:
```js
export const SUPABASE = {
  url: 'https://abcd.supabase.co',
  anonKey: 'المفتاح-العام',
  rsvpFunctionUrl: '',   // فارغ = `${url}/functions/v1/rsvp`
};
```

> ⛔ **لا تضع أبدًا** مفتاح `service_role` أو `sb_secret_...` في `js/config.js` أو أي ملف آخر في المشروع.

## اختبار الموقع قبل النشر

شغّل `node scripts/serve.mjs` (مع إضافة `http://localhost:5173` إلى `ALLOWED_ORIGINS`) ثم:

**اختبار الردود**
- [ ] أرسل ردًا بالحضور (عدد 2) → تظهر رسالة النجاح، والرد في **Table Editor → rsvp_responses**.
- [ ] أعد تحميل الصفحة → تظهر رسالة «سبق أن سجّلتم ردكم» ويمكن التعديل دون إنشاء رد جديد.
- [ ] أرسل اعتذارًا من متصفح آخر → `guest_count = 0`.
- [ ] جرّب اسمًا فارغًا وعددًا 0 أو أكبر من الحد → رسائل خطأ ولا يُرسل شيء.
- [ ] افصل الإنترنت وأرسل → رسالة خطأ مفهومة، والبيانات باقية في النموذج.

**اختبار لوحة الإدارة**
- [ ] سجّل الدخول من `/admin/` → الأرقام تطابق الجدول.
- [ ] عدّل ردًا واحذف آخر → تتحدث الإحصائيات فورًا ويظهران في «سجل العمليات».
- [ ] صدّر CSV وافتحه في Excel → العربية تظهر صحيحة.
- [ ] أنشئ دعوة شخصية وافتح رابطها في نافذة خاصة.
- [ ] سجّل الخروج → العودة لصفحة الدخول.

**التحقق من الحماية يدويًا** (يجب أن تُرفض كلها):
```bash
curl "https://abcd.supabase.co/rest/v1/rsvp_responses?select=*" \
  -H "apikey: المفتاح-العام" -H "Authorization: Bearer المفتاح-العام"
# المتوقع: permission denied for table rsvp_responses

curl -X POST "https://abcd.supabase.co/rest/v1/rpc/rsvp_submit" \
  -H "apikey: المفتاح-العام" -H "Authorization: Bearer المفتاح-العام" \
  -H "Content-Type: application/json" -d '{}'
# المتوقع: permission denied for function rsvp_submit (أو not found)
```

بعد التأكد، **احذف الردود التجريبية** من لوحة الإدارة قبل مشاركة الرابط.

## النشر

الموقع ثابت بالكامل؛ اختر أي استضافة:

### Netlify (موصى به للبساطة)
1. **Add new site → Deploy manually** واسحب مجلد المشروع (بعد ضبط `js/config.js`)، أو اربطه بمستودع Git.
2. لا يوجد أمر بناء؛ مجلد النشر هو الجذر (`netlify.toml` جاهز ويضيف ترويسات أمان ويحجب `tests/` و`supabase/` و`scripts/`).

### Vercel
`vercel deploy` من المجلد، أو اربط المستودع واختر Framework = **Other** بدون أمر بناء. (`vercel.json` و`.vercelignore` جاهزان.)

### GitHub Pages
ارفع المشروع لمستودع، ثم **Settings → Pages → Deploy from branch → main / root**.
ملاحظة: GitHub Pages سينشر مجلدات `tests/` و`supabase/` أيضًا؛ لا تحتوي أي أسرار، لكن يمكنك حذفها من فرع النشر إن أردت.
إذا كان الموقع على مسار فرعي (`username.github.io/repo/`) فكل الروابط نسبية وتعمل كما هي.

### Cloudflare Pages
**Create project → Direct upload** أو ربط Git، بدون أمر بناء، ومجلد الإخراج `/`.

### بعد النشر
1. حدّث سر الدالة: `supabase secrets set ALLOWED_ORIGINS="https://your-domain.example"`.
2. ضع `PUBLIC_SITE_URL` (أو `UI.siteUrl` في `js/config.js`) برابط الموقع ليظهر في رسالة واتساب وروابط الدعوات.
3. حدّث **Site URL** في إعدادات Supabase Auth.

### الدومين المخصص
- **Netlify/Vercel/Cloudflare**: أضف الدومين من إعدادات الموقع واتبع تعليمات DNS (سجل CNAME أو A)، ويُصدر شهادة HTTPS تلقائيًا.
- **GitHub Pages**: أضف الدومين في Settings → Pages، وسجل CNAME يشير إلى `username.github.io`، وفعّل **Enforce HTTPS**.
- لا تنسَ إضافة الدومين الجديد إلى `ALLOWED_ORIGINS`.

### قائمة التحقق قبل مشاركة الرابط
- [ ] الصفحة تفتح على الهاتف والكمبيوتر عبر HTTPS.
- [ ] العد التنازلي صحيح والتاريخ «الخميس 27 مايو 2027».
- [ ] رد تجريبي يصل للوحة الإدارة (ثم احذفه).
- [ ] زر الخرائط يفتح الموقع الصحيح (أضف الرابط الدقيق من الإعدادات إن توفر).
- [ ] رسالة واتساب تحتوي رابط الموقع وملاحظة الأطفال.
- [ ] `ALLOWED_ORIGINS` مقيّد بدومينك، والتسجيل العام في Supabase Auth معطّل.

## الدعوات الشخصية والرابط العام

يدعم النظام طريقتين (يمكن استخدامهما معًا):

| | الرابط العام | الدعوة الشخصية |
|---|---|---|
| الرابط | `https://site/` | `https://site/#i=رمز-سري` |
| منع التكرار | **غير مضمون بالكامل** | **رد واحد لكل دعوة** (مفروض في القاعدة) |
| تعديل الرد | من نفس المتصفح والجهاز فقط (رمز تعديل سري يُحفظ محليًا) | من أي جهاز عبر نفس الرابط |
| الحد الأعلى | الحد العام من الإعدادات | حد خاص اختياري لكل دعوة |
| حساب «لم يرد بعد» | غير ممكن | ممكن |

- رمز الدعوة 192 بت عشوائي (32 حرفًا)، لا يمكن تخمينه، ولا يُخزَّن في القاعدة إلا **بصمته (SHA-256)**؛ لذلك يظهر الرابط مرة واحدة عند الإنشاء.
- الرمز في جزء `#` من الرابط، فلا يُرسل إلى خادم الاستضافة ولا يظهر في ترويسة Referer.
- **حدود الأمان**: أي شخص يحصل على رابط دعوة شخصية يستطيع الرد أو التعديل باسمها. إن تسرّب رابط، استخدم «رابط جديد» من لوحة الإدارة (يُبطل القديم فورًا) أو «إلغاء».
- في الرابط العام: الإرسال المتكرر من نفس الجهاز يتحول إلى تعديل، وإعادة المحاولة بعد انقطاع الشبكة لا تكرر الرد. لكن شخصًا يستخدم أجهزة أو متصفحات مختلفة يمكنه إرسال أكثر من رد. لإلغاء هذا الاحتمال: أنشئ دعوات شخصية للجميع، ثم أوقف «السماح بالرد عبر الرابط العام» من الإعدادات.

## الإعدادات القابلة للتعديل

**من لوحة الإدارة ← إعدادات الحفل** (تُحفظ في `wedding_settings` وتظهر في الصفحة عند فتحها أو تحديثها). ترك حقل اختياري فارغًا يُخفي عنصره من الصفحة:

| القسم | الحقول | الافتراضي |
|---|---|---|
| العروسان | اسم العريس، اسم العروس * | يوسف، شذى |
| الموعد | التاريخ *، الوقت *، المنطقة الزمنية *، مدة الحفل | 2027-05-27، 16:00، `Asia/Baghdad`، غير محددة (التقويم يستخدم 240 دقيقة تقديرية مع تنبيه) |
| المكان والموقع | اسم القاعة *، العنوان *، رابط Google Maps الدقيق (`https://`) | مزرعة الفرح، العابات على نهر دجلة، فارغ ← رابط بحث |
| نصوص الافتتاحية | الآية/العبارة الافتتاحية، السطر فوق الأسماء، السطر تحت الأسماء، نص الدعوة | النصوص الحالية للصفحة |
| عناوين الأقسام | عنوان الموعد *، عنوان العد التنازلي *، رسالة حلول الموعد *، عنوان المشاركة *، عنوان نموذج الرد *، النص تحته، عبارة التذييل | النصوص الحالية |
| ملاحظة الأطفال | إظهار/إخفاء، العنوان *، النص (كل سطر = فقرة) | ظاهرة، بالنص الحرفي المطلوب |
| المشاركة وواتساب | رابط الموقع المنشور، رقم واتساب (دولي)، العبارة الختامية | فارغ، فارغ (يختار الضيف جهة الاتصال)، «حضوركم يزيدنا فرحًا وشرفًا…» |
| تأكيد الحضور | الحد الأعلى للبالغين *، آخر موعد، استقبال الردود، الرابط العام، زر التقويم | 5 (قيمة مبدئية)، فارغ، نعم، نعم، نعم |

كل القيود (الأطوال، `https://`، صيغة الرقم، المنطقة الزمنية الصحيحة، الحقول المطلوبة) تُفرض في قاعدة البيانات أيضًا،
ولا يستطيع تعديلها إلا مدير مسجَّل في `admin_users`، وكل تعديل يُسجَّل في سجل العمليات.

**من `js/config.js`**: رابط Supabase والمفتاح العام فقط بشكل أساسي، إضافة إلى المدة التقديرية للتقويم و`whatsappNumber`/`siteUrl` الاحتياطيين (قيم اللوحة لها الأولوية)،
والقيم الافتراضية التي تظهر لحظيًا قبل تحميل الإعدادات من الخادم (أو إن تعذّر الاتصال).

## الأمان وحدوده

**ما هو منفّذ ومُختبر فعليًا** (انظر `TEST_REPORT.md`):
- RLS مفعّل على كل الجداول، والصلاحيات الافتراضية لـ `anon`/`authenticated` مسحوبة صراحة.
- الزائر المجهول لا يقرأ ولا يعدّل ولا يحذف أي رد، ولا يستدعي أي دالة RSVP أو إدارية مباشرة.
- المستخدم المسجّل غير المدير يرى 0 صفوف ولا يستطيع التعديل أو ترقية نفسه.
- المدير لا يستطيع تعديل أعمدة حساسة (`edit_token_hash`، `token_hash`، `invitation_id`) إلا عبر الدوال المخصصة.
- القيود الحاسمة في القاعدة: الاسم غير فارغ (2–80)، الحالة `attending|declined` فقط، العدد ≥ 1 عند الحضور و= 0 عند الاعتذار، والحد الأعلى من الإعدادات أو الدعوة.
- التحقق مكرر في الواجهة والدالة والقاعدة.
- تحديد معدل الطلبات لكل IP (العنوان يُجزّأ بملح سري ولا يُخزّن)، وحقل فخ للروبوتات، وحد لحجم الطلب.
- رسائل الأخطاء للزائر عامة ولا تكشف تفاصيل داخلية.
- سجل التدقيق إلحاقي ومحمي من التعديل والحذف والتفريغ، ولا يحتوي رموزًا أو كلمات مرور.
- لا تُجمع أرقام هواتف ولا بيانات حساسة؛ فقط الاسم والحضور والعدد والرسالة.
- CSP صارمة (`script-src 'self'`)، و`Referrer-Policy: no-referrer`، وروابط خارجية بـ `noopener noreferrer`.
- تصدير CSV يعطّل الصيغ (`= + - @`).

**حدود يجب معرفتها:**
- الرابط العام لا يمنع التكرار بشكل مطلق (انظر القسم السابق).
- تحديد المعدل حسب IP يمكن تجاوزه بتغيير الشبكة، وقد يتشارك عدة ضيوف نفس IP (مثل شبكة جوال)؛ الحد الافتراضي 10 إرسالات/10 دقائق لكل IP، وهو قابل للتعديل.
- لا يوجد CAPTCHA؛ يمكن إضافة Cloudflare Turnstile لاحقًا إن ظهر إرسال آلي.
- أمان حساب المدير يعتمد على قوة كلمة مروره؛ يُنصح بكلمة مرور طويلة فريدة. يمكن تفعيل MFA في Supabase مستقبلًا.
- مالك قاعدة البيانات (`postgres`) يستطيع تقنيًا تعطيل محفزات حماية السجل؛ الحماية موجهة ضد الوصول عبر API.
- رسالة واتساب تُجهَّز فقط؛ المستخدم هو من يختار جهة الاتصال ويضغط إرسال. لا يُرسل الموقع أي رسالة تلقائيًا.
